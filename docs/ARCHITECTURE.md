# Architecture

The system follows a standard 4-layer IIoT design:

```
Sensor Layer  -->  Communication Layer (MQTT)  -->  Cloud Layer  -->  Application Layer
```

## 1. Sensor Layer (`/sensor-nodes`)

Four virtual sensor processes (`sensor_node.py`, one container per
`NODE_ID`) simulate temperature, vibration, pressure, and humidity
transducers on a single production line (`line1`). Each node:

- Maintains a random-walk baseline (drift) plus Gaussian noise, so readings
  look like a real analog sensor rather than random numbers.
- Publishes a JSON payload every 5 seconds (configurable) to its own topic,
  e.g. `factory/line1/temperature`.
- Subscribes to a per-node control topic
  (`factory/control/anomaly/<node_id>`) so an anomaly can be injected either
  randomly (`ANOMALY_PROBABILITY` env var) or on demand from the dashboard,
  for demoing the alert pipeline.

Payload shape:

```json
{
  "node_id": "temp-line1",
  "sensor_type": "temperature",
  "value": 91.4,
  "unit": "C",
  "anomaly": true,
  "timestamp": "2026-01-01T12:00:00.000000+00:00"
}
```

## 2. Communication Layer (`/broker`)

Eclipse Mosquitto, configured for:

- **TLS** on port 8883 using a self-signed CA generated by
  `broker/generate-certs.sh` (swap for a real CA in production — see
  [SECURITY.md](SECURITY.md)).
- **Username/password auth** (`password_file`), with the password file
  generated at stack startup by the `mqtt-credentials-init` one-shot
  service so no manual step is required.
- **Topic ACLs** (`acl.conf`): the `sensor` user may only *publish* to
  `factory/+/+` and *subscribe* to `factory/control/#`; the `backend` user
  may only *subscribe* to `factory/#` and *publish* to `factory/control/#`
  (used to relay dashboard-triggered anomaly commands back down to a
  sensor). Neither can do anything outside that scope.

## 3. Cloud Layer (`/backend`)

A FastAPI service (`app/mqtt_client.py`) subscribes to `factory/#` over the
same TLS+auth connection. For every message it:

1. Parses and validates the JSON payload against a Pydantic schema
   (`SensorReading`), dropping anything malformed.
2. Re-stamps the timestamp only if the device-supplied one is unparsable —
   otherwise the original sensor timestamp is preserved for accuracy.
3. Writes the reading to **InfluxDB** (`sensor_reading` measurement, tagged
   by `node_id`/`sensor_type`).
4. Runs it through the **rules engine** (`app/rules.py`), which checks
   configurable thresholds per sensor type (`backend/rules.yaml`). A
   breach creates an `Alert`, written to InfluxDB (`alert` measurement) and
   broadcast immediately over WebSocket. A per-rule/per-node cooldown
   (30s) prevents alert flooding while an anomaly episode is ongoing.
5. Broadcasts the raw reading over WebSocket to any connected dashboards.

REST endpoints (all except `/api/auth/login` and `/api/health` require a
JWT bearer token):

- `POST /api/auth/login` — exchanges username/password for a JWT.
- `GET /api/readings/history` — historical query from InfluxDB
  (`node_id`, `sensor_type`, `hours` filters).
- `GET /api/readings/nodes` — list of node ids seen so far.
- `GET /api/alerts` — recent alerts from InfluxDB.
- `GET /api/status` — MQTT/InfluxDB connectivity + connected WebSocket
  client count, for the dashboard's status bar.
- `POST /api/control/anomaly/{node_id}` — publishes a control message that
  the target sensor node subscribes to.
- `WS /ws?token=...` — live stream of `{"type": "reading" | "alert", "data": ...}`
  frames.

## 4. Application Layer (`/dashboard`)

A Vite + React SPA:

- Login screen exchanges credentials for a JWT (stored in
  `localStorage`), attached as a `Bearer` token to all REST calls and as a
  query param on the WebSocket URL (browsers can't set custom headers on
  WebSocket handshakes).
- **Live Sensor Readings** — most recent value per node, updated instantly
  via WebSocket.
- **Historical Trend** — `recharts` line chart backed by
  `GET /api/readings/history`, polled every 10s, with node/time-range
  selectors.
- **Active Alerts** — live-updating list, seeded from
  `GET /api/alerts` and appended to via WebSocket.
- **Status bar** — live-feed, MQTT, and database connectivity indicators
  from `GET /api/status`, polled every 5s.

## Data flow summary

```
sensor (publish, TLS+auth) -> mosquitto (ACL-checked) -> backend (subscribe)
   -> validate + timestamp -> InfluxDB (store)
                            -> rules engine -> alert? -> InfluxDB (store)
   -> WebSocket broadcast (reading, and alert if any) -> dashboard (render)
```
