# Security Model

This is a local demo/prototype. The mechanisms below are real and
functional, but the default secrets in `.env.example` are for development
only — **rotate every credential before any non-local use.**

## Transport security: MQTT over TLS

- The broker listens only on port 8883 with TLS enabled
  (`broker/config/mosquitto.conf`: `cafile`/`certfile`/`keyfile`).
- Certificates are self-signed for local dev, generated by
  `broker/generate-certs.sh` into `broker/certs/`:
  - `ca.crt` / `ca.key` — a local root CA.
  - `server.crt` / `server.key` — the broker's certificate, signed by that
    CA, with `subjectAltName` covering `mosquitto`, `localhost`, `127.0.0.1`.
- All MQTT clients (sensor nodes, backend) are configured with
  `cert_reqs=ssl.CERT_REQUIRED` and the CA cert, so they verify the
  broker's identity — this is not `tls_insecure_set(True)`.

**Swapping in real certificates for production:** replace
`broker/certs/server.crt` and `server.key` with a certificate issued by a
real CA (e.g. Let's Encrypt, or an internal PKI) for your broker's real
hostname, and distribute that CA's public certificate as `ca.crt` to every
client. No code changes are required — only the files change.

## MQTT authentication and authorization

- `allow_anonymous false` — no client can connect without credentials.
- `password_file` — bcrypt-hashed credentials for two accounts: `sensor`
  (shared by all sensor node containers) and `backend`.
- `acl_file` — least-privilege topic ACLs:
  - `sensor`: **publish-only** on `factory/+/+` (its own readings) and
    **subscribe-only** on `factory/control/#` (to receive anomaly-trigger
    commands). It cannot read other sensors' data or publish control
    commands.
  - `backend`: **subscribe-only** on `factory/#` and **publish-only** on
    `factory/control/#` (to relay dashboard-triggered commands). It cannot
    impersonate a sensor.

This means a compromised sensor-node container cannot eavesdrop on other
sensors' data or issue control commands, and the backend cannot spoof
sensor readings.

## API authentication

- The dashboard exchanges credentials for a JWT via
  `POST /api/auth/login` (HS256, `JWT_SECRET`, configurable expiry —
  default 8 hours).
- Every REST endpoint except `/api/auth/login` and `/api/health` requires
  a valid `Authorization: Bearer <token>` header (`app/auth.py`,
  `get_current_user` dependency).
- The WebSocket endpoint (`/ws`) validates the same JWT passed as a
  `?token=` query parameter, since browsers cannot attach custom headers
  to a WebSocket handshake. Connections with a missing/invalid/expired
  token are closed immediately with policy-violation code 1008.
- Passwords are never stored or compared in plaintext — the demo user's
  password is bcrypt-hashed at process start (`passlib`).

## Data validation

- Every inbound MQTT payload is parsed as JSON and validated against a
  strict Pydantic schema (`SensorReading`) before it touches storage or the
  rules engine. Malformed or schema-violating payloads are logged and
  dropped rather than propagated.

## Secrets management

- All credentials (MQTT users, InfluxDB admin token, JWT secret, demo
  login) are supplied via environment variables / `.env` files, never
  hardcoded beyond development-only fallback defaults, and `.env` files are
  gitignored.
- `broker/certs/*.key` and `broker/config/passwd` are also gitignored —
  they're generated locally by the setup scripts, not checked in.

## Known limitations (acceptable for a local demo, not for production)

- The `sensor` MQTT credential is shared across all sensor containers
  rather than per-device — a production deployment should issue unique
  credentials (or better, client certificates) per physical device.
- CORS is restricted to configured localhost origins but the demo JWT
  secret/InfluxDB token defaults are static — must be rotated before any
  shared or internet-facing deployment.
- There is no rate limiting on the login endpoint.
